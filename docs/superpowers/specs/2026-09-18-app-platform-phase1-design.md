# Monolith application platform, Phase 1: design

Date: 18 September 2026. Owner-approved decisions (Q1–Q18 of the design interview) are locked for Phase 1 unless implementation exposes a real blocker in tenant isolation, payment integrity, authentication, source-of-truth ownership, deployment boundary, or production cost/security.

## Goal

A production-shaped foundation for client billing: an opaque-link payment page (`pay.mnlith.dev`), an authenticated client portal (`portal.mnlith.dev`), a server-side application API, and a D1 application database, proven end to end in Stripe test mode with automated tests. Smallest correct foundation, not the largest feature set.

## Three data domains (never merged)

| Domain | Store | Owner of truth |
|---|---|---|
| PSA data (tickets, companies, contacts, agreements) | external PSA system used by the MONOLITH internal app | External PSA vendor. **Out of scope. Nothing in this repo touches, references, or imports the external PSA vendor.** |
| Public website inquiries | D1 `monolith-inquiries` (Worker `monolith-api`) | Existing. Untouched. |
| Portal, invoices, payments, memberships | **New** D1 `monolith-app` (new Worker `monolith-app`) | Authoritative for the billing domain. |

## Topology (Q1, Q12)

- Same repository, new `app/` directory. One new Worker `monolith-app`: Hono script + static assets (portal SPA build), routed by hostname from environment variables `PAY_HOST`, `PORTAL_HOST`, `ADMIN_HOST` (reserved). Unknown host: 404.
- Production hostnames (no DNS in Phase 1): `pay.mnlith.dev`, `portal.mnlith.dev`; `admin.mnlith.dev` reserved for the future internal boundary. `api.mnlith.dev` stays inquiry-only.
- Development: `PORTAL_HOST=localhost`, `PAY_HOST=127.0.0.1` (two hostnames on the same loopback interface, so the hostname router and the Stripe CLI both work without a hosts-file entry; Node tests set the `Host` via the request URL). Earlier drafts used `pay.localhost`, which non-browser clients on Windows cannot resolve.
- Stack (Q2): Hono, `@clerk/backend`, `stripe` official SDK, `@clerk/clerk-react`, exact pinned versions. No hand-rolled JWT or webhook cryptography. Tests stay on `node:test` with the SQLite-backed D1 adapter pattern.
- Static assets: `run_worker_first: true`; the Worker serves the portal SPA through the `ASSETS` binding only on the portal host (`not_found_handling: single-page-application`). The pay host never serves static assets.
- Every response carries security headers set by the Worker. Pay-host CSP: `default-src 'none'; style-src 'self'; img-src 'self'; form-action 'self' https://checkout.stripe.com; base-uri 'none'; frame-ancestors 'none'`. Portal CSP is built from `CLERK_FRONTEND_API_URL` (Clerk's documented CSP requirements) plus `'self'`; `connect-src` includes `'self'` and the Clerk frontend API only.

## Data model (Q16 and the owner's schema)

D1 `monolith-app`, versioned migrations only (`app/migrations/`). Tables: `clients`, `memberships`, `services`, `invoices`, `invoice_items`, `payment_links`, `payments`, `payment_events`, `audit_events`, plus reserved `staff_api_keys` (no code uses it). IDs are UUID text; timestamps are Unix seconds; money is integer cents with a currency code (`usd`). `external_source` / `external_id` columns on `clients` and `invoices` reserve future integrations. Invoice numbers `MON-00001` are generated by the app (zero-padded, unique). The full DDL is in the implementation plan.

Invoice status: `draft → open → processing → paid`, plus `void`. Card payments go `open → paid`; ACH goes `open → processing → paid`, and failure returns `processing → open`. Payments have their own status (`pending`, `processing`, `succeeded`, `failed`, `canceled`) and one row per Stripe Checkout Session.

## Payment links (Q6)

32 cryptographically random bytes, base64url (43 chars). D1 stores only the SHA-256 hex of the token in `payment_links.token_hash`. One active link per invoice (partial unique index), revocable and regenerable. Malformed or unknown token, revoked link, or void invoice: generic 404. Paid invoice: a small "already paid" page with number, amount and paid date; no payment action. The plaintext token is never logged or stored.

## Payment flow (Q3, Q7, Q8)

- Pay page is server-rendered HTML from the Worker: no Clerk, no framework JS, no analytics. It loads the authoritative invoice by token hash and shows number, description, line items, amount due, and a "Pay" form that POSTs to the Worker. The Worker creates a Stripe Checkout Session (`mode: payment`, `usd`, server-side amount from D1, `client_reference_id` = invoice id, `metadata` = invoice id/number/payment id, `expires_at` = now + 30 min, idempotency key = payment id) and 303-redirects to Stripe. Payment method selection is Stripe's automatic payment methods (card and `us_bank_account` enabled in the Stripe dashboard by the owner).
- A pending, unexpired Checkout Session for the same invoice is reused rather than creating a second one.
- Full payment only. No partial or over-payment, no refund UI. Refund and dispute events are recorded in `payment_events` for history but do not change invoice state in Phase 1.
- Webhook `POST /api/stripe/webhook` on the pay host: signature verified with `constructEventAsync` + `createSubtleCryptoProvider()`; livemode must match `STRIPE_MODE`; `payment_events.stripe_event_id` is UNIQUE, and the event insert plus all state changes are applied in one atomic `batch`, so a replay is a no-op returning 200. Amount mismatch between session and invoice is recorded as `mismatch` and never marks the invoice paid. Events for unknown sessions are recorded as `unmatched`. State transitions are conditional updates (`WHERE status IN (...)`) so out-of-order delivery cannot regress state.

## Identity and authorization (Q5, Q18, Q17)

- Clerk proves identity. The portal SPA sends `Authorization: Bearer <session JWT>`; the Worker verifies it with `@clerk/backend` (`verifyToken`, networkless via `CLERK_JWT_KEY` when present, `authorizedParties` = portal origin).
- Membership binding on first login: verify session → `sub` → Clerk Backend API `users.getUser(sub)` → primary email, verified → match `memberships` row with that email and status `invited` and no `clerk_user_id` → bind `clerk_user_id`, status `active`, audit event. After binding, authorization uses `clerk_user_id` + membership only; no further email lookups. Unmatched authenticated user: 403 `no_account`, generic "No account linked" screen. No self-service enrollment. No Clerk Organizations.
- Every portal API query is scoped by the caller's `client_id`. A resource belonging to another client returns 404 (not 403). Nothing relies on client-side routing for authorization.
- Staff/admin API (MONOLITH internal app → `monolith-app`): documented contract only. `Authorization: Bearer mk_<secret>` (random credential, hash stored server-side, scoped, revocable, rate-limited, admin host only; Cloudflare Access service tokens as production hardening). Not implemented in Phase 1; `staff_api_keys` table reserved. MONOLITH is a Next.js server-side app; the credential stays server-side.

## Portal (Q4)

Vite + React 19 SPA under `app/portal`, Clerk React SDK, brand tokens and fonts from the site. Phase 1 screens: sign-in, overview (account, balance), invoices list, invoice detail with Pay (creates a portal-sourced Checkout Session), services, and "No account linked". Publishable key comes from `GET /api/public-config` at runtime, so one build serves every environment. A dev-only preview mode (`VITE_PORTAL_PREVIEW=1`, `vite dev` only) renders the screens from in-memory fake data for visual review without Clerk credentials; it is compiled out of production builds.

## API (portal host, Clerk session + membership required unless noted)

```
GET  /api/public-config              (public) { clerkPublishableKey }
GET  /api/me                          { user, membership, client, balanceCents }
GET  /api/clients/:id                 own client only, else 404
GET  /api/services
GET  /api/invoices[?status=]
GET  /api/invoices/:id                invoice + items + payments
POST /api/invoices/:id/checkout       201 { url } ; 409 if not open
POST /api/stripe/webhook              (pay host; Stripe signature only)
GET  /healthz                         (both hosts) { status: "ok" }
```

## Testing (Q10, Q11)

Offline-verifiable with fakes for Clerk (session verifier, user lookup) and Stripe (gateway, webhook verifier); real SQLite executes the real migrations and SQL; the real Stripe verifier is exercised with SDK-generated test signatures. Required cases: migrations; tenant isolation; malformed, unknown, revoked, paid and void tokens; first-login binding; unmatched user; signature failure; replay idempotency; card and ACH transitions including failure; cross-client denial; XSS escaping on the pay page; CSP headers. No real Clerk or Stripe credentials; no production keys; secrets only in `app/.dev.vars` (git-ignored).

## Out of scope for Phase 1

No external PSA/CRM vendor integration is in scope; admin/staff API implementation; DNS, Custom Domains, remote D1 creation, Workers Paid, live Stripe, Clerk production instance (all owner approvals); partial payments/refunds; Turnstile (token entropy makes brute force infeasible; add only on observed abuse); email notifications; privacy-policy text changes (required changes are listed in `app/README.md` for the owner).
